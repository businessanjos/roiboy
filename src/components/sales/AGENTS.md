Triggered by the seller's screen (`MeetDriveSyncBar`, ≤1 per 30 min) or `x-cron-secret`. Why: per-user Google consent, no shared credentials, never imports the same file twice.
- Pending `meet_drive` sessions are analyzed without a click by `meet-call-auto-analyze` (managed cron schedule), which claims rows atomically (`pending`→`analyzing`), writes `analysis`/`analysis_status`, and pauses the account in `meet_analysis_state` on AI credit/access failures. Prompt, models and output limits live once in `supabase/functions/_shared/salesCallAnalysis.ts`, shared with the manual `analyze-sales-call`. Why: one prompt for both routes and no double analysis.
- Pipeline company filtering is local, user-persisted, independent of the global company selection and shared across open/won/lost through `filterDealsByCompany`; it reads only each deal's stored `company_id` from the RLS-scoped query. Why: clients remain shared and historical sales must not be reclassified from the current product catalog.
- Pipeline bulk actions use authenticated invoker RPCs and insert triggers to commit each change with immutable server-derived audit snapshots; access comes from `can_bulk_edit_deals`, while existing deal RLS, required-stage fields and SDR routing remain in force. Bulk moves preserve open/won/lost status and closed-deal probability without reopening; undo compares the current status to the saved snapshot. History lives in `bulk_deal_operations`/`_items`; own latest move undo uses locked snapshots, a complete server count and an atomic invoker update, never client-supplied before values. Why: audit and undo must not widen access, replay closing effects, overwrite later changes or partially restore a batch.
- Individual revenue-field edits use `mqlFromRevenue` in `src/lib/sales/bulkDeals.ts`; the transactional bulk trigger applies the same thresholds using the saved option label. Why: qualification rules must stay identical across both editing paths.
- Pipeline workspace keeps search and pipeline visible; secondary filters live in a demand-open Sheet, and nested filter/calendar popovers portal inside it. Why: filter density must not consume board height or break modal focus and scrolling.
- Kanban edge navigation observes only its horizontal scroller and content, shows a right arrow while more stages remain and flips to a left arrow at the end, hides when there is no overflow or during dragging, and respects reduced motion. Why: overflow cues must not intercept card scrolling or deal dragging.
- Pipeline ordering is a cancellable draft in the selector, saved through existing authenticated `pipelines.display_order` updates scoped to account, active row and previous order; only visible slots change and failures reconcile from the server. Why: organizing funnels must preserve access, hidden funnels, selected pipeline and all deal/stage data without new backend rules.
- Pipeline, filter preview and export compare Item da Venda via presentation-only `matchesPipelineItemVenda` (saved option/slug/product UUID, exact catalogue fallback, distinct renewals); custom-filter reads use paginated `usePipelineFilterValues` keyed by account, user, deals, requested fields and revision, with draft fields loaded independently. Why: badges and saved filters must agree without rewriting records or treating missing pages as empty fields.
- A funnel's name is a display label only: rules identify funnels by `pipelines.system_role` through `src/lib/sales/pipelineRoles.ts` (server-maintained with `previous_names`; clients cannot write either). Renaming goes through the edit dialog's `PipelineRenameNotice` (impact from RPC `pipeline_rename_impact`), and the rename trigger updates saved Insights `pipeline_name` filters of the same account and logs `pipeline_name_history`. Why: a rename once emptied dashboards and left leads without deals.
- The subscription question at win time is driven by `companies.requires_subscription_on_win` (never the company name) against the deal's stored `company_id`; the answer lives in `deals.is_subscription`/`subscription_cycle`, the allowed "Forma da Pagamento" values per cycle live only in `src/lib/sales/subscriptionWin.ts`, and every win entry point checks `fetchSubscriptionWinState` (Pipeline and RoyZapp in their own win flow, other screens through `DealDetailSheet`'s gate) and collects it in `RequiredFieldsModal`. Why: one rule for all win paths that survives company renames and new companies.
- Deal activity indicators (`get_deal_activity_stats`, RoyZapp deal task lists) count a task on its own deal only; tasks with no deal still count through the shared lead/client. Why: a pending task of another deal of the same contact painted cards overdue with nothing to do.
- In `RequiredFieldsModal`, when the subscription question applies, every other win field stays hidden until it is answered (and the cycle chosen when it is a subscription); saving is still validated by `isSubscriptionAnswerComplete`. Why: payment method options depend on the answer, so filling them first breaks the flow.
- The deal card's "Assinaturas" (RykaPay) tab is gated by `canShowPaySubscriptions` (src/lib/sales/paySubscriptionsTab.ts) and its content mounts only when shown. Why: before the win there is no subscription, so nothing should be displayed or queried.
- In the win flow, a subscription never asks for a number of installments (`withoutInstallmentChoice` stores one charge per line) and, once the cycle is chosen, `RequiredFieldsModal` reads RykaPay through the existing `rykapay-read` path; `paidPayCharge` (src/lib/sales/subscriptionPayCharge.ts) locks value and first-payment date as read-only only for a complete answer with a paid charge of that cycle, otherwise the seller fills by hand. Why: billing lives in RykaPay, and unknown or partial data must never be shown as a confirmed payment.
