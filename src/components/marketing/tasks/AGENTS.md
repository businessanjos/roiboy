# Marketing task details

- Delivery time, requester identity and label color metadata live in `marketing_tasks.custom_fields.delivery_details`; label names remain in `tags`, and execution ownership remains in `assignee_id`. Why: add task identification without schema, permission or audit-identity changes, retaining legacy fields.
- Duplication opens an editable unsaved draft, resets completion and copies child tasks only after creating a new parent through the current user's client; compensate a failed child insert by deleting only that new parent. Why: never modify the source or leave a silent partial copy.
- `taskDetails.ts` is shared by editing, duplication, filtering and date/time sorting; `TaskPeopleAndLabels` renders both views. Why: labels and delivery metadata must agree without duplicate interpretations.
- Filter and task editor share `TaskLabels` and `useMarketingTaskLabelCatalog`; unused labels are local to account/user/browser, saved task tags remain the shared catalogue, and creating a filter option never selects it automatically. Why: allow frontend-only creation without phantom tasks, accidental empty boards or backend changes.
- New attachments use private `marketing-task-files` paths and short-lived signed reads; legacy URLs still work. Detaching saved attachments never deletes shared objects, and only this draft's newly uploaded unused paths are cleaned up. Why: cancellation and duplicate edits must not destroy another task's attachments.
- Covers live in `custom_fields.card_cover` and refer to an attachment identity or semantic color; comments live in `marketing_task_comments` with server-stamped author/time and task-scoped RLS, and are not duplicated. Why: keep collaboration attributed and avoid stale signed URLs in stored metadata.
- Named board dividers live separately in `marketing_task_separators`, anchored before a task within a column and rendered by `taskBoardItems`; moving/deleting them never changes task data or counts. Why: a divider is not a task, calendar entry or project demand.
- Task descriptions remain plain text in `description`, with a sanitized Tiptap JSON snapshot and custom highlight colors in `custom_fields.description_editor`; only matching snapshots are restored. Why: preserve plain-text integrations and legacy edits without rendering arbitrary saved HTML.
- Task web links share `taskLinks` sanitization and existing Tiptap autolink; only credential-free HTTP(S) links open in a separate tab without an opener, and hydration never autosaves. Why: legacy, typed, pasted and comment links must preserve their full destination and reject executable schemes.
- Description timestamps share `taskTimestampRanges` for editor transactions and sanitized snapshots; automatic bold never changes plain text or comment behavior. Why: typing, pasting and reopening must format the same timestamps without bold spilling into subsequent text.
- Editable task dates use `TaskDeliveryDate` with strict pt-BR text parsing and the existing ROY calendar; invalid/partial text blocks save. Time-first drafts infer their local calendar day through `resolveTaskDeliveryDate`, tracking automatic versus explicit dates only in the draft. Why: allow either input order without replacing chosen/partial dates, changing saved tasks or shifting calendar days.
- Task dialog submit and save availability share `hasTaskResponsible`; requester remains independent, and missing/technical assignees require an explicit choice without rewriting legacy tasks. Why: the same validation applies to creation, editing and duplicate drafts without changing backend rules.
- Board expansion keeps the same task/filter state in a viewport overlay, uses full-height column scroll areas and leaves task dialogs portaled above it; Escape closes a dialog before the board. Why: gain working space without losing context or blocking task actions.
- Task editing scrolls content and metadata independently on desktop, with attachments/covers beside the description; mobile uses one body scroller. Why: a tall metadata column must not create a blank tail in the content column.
- Task comments reuse the description toolbar and store formatted content as versioned sanitized JSON in the existing body; plain comments stay plain, rendering uses React nodes, and alignment uses the individual author ID. Why: retain formatting and legacy comments without schema, permission or identity changes or interpreting arbitrary HTML.
- Comment notifications originate from the server INSERT trigger, deduplicated per comment/recipient; it validates same-account responsibility and Marketing mentions, excludes the author, and resolves typed first names only when unique. Why: clients must not forge recipients or lose alerts when a task closes.
- Comment mentions use Tiptap Mention with explicit person IDs and the existing filtered Marketing people source; notification task/comment links open only user-readable tasks, independently of board filters. Why: first names are not identities and links must preserve access and context.- Task search goes through `taskSearch` (accent/case-insensitive, all words required) over title, description, labels, people, attachment names and subtask titles; subtask titles load read-only only while a search is typed. Why: list, board and counts must match the same content without loading extra data when idle.
