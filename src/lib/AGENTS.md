# AGENTS.md — src/lib

- Team numbers are never clients: `public.internal_client_split(p_account_id)` (SECURITY INVOKER over `zapp_internal_contacts` + `hr_collaborators` phone cores) returns `all` (every team number) and `hidden` (the ones registered in `zapp_internal_contacts`). `hidden` is removed from the `list-clients` rows and from global search, finance client badge and MCP counts; the rest of `all` stays in the client list marked "Interno" and is subtracted from client totals. `src/lib/internalClients.ts` + `useInternalClientIds` are the app-side path and `isInternalClientRecord` in `src/lib/zappInternalContacts.ts` covers client records. Why: a colleague's number registered as a client must not be counted or exported as a client, but the team still needs to find the record.
- Clínica Ryka usage: `sync-ryka-clinics` (daily cron + button) matches eligible clients by product-name substring, stores match in `client_ryka_provisions.ryka_response` and, when the Ryka API answers `action=clinic_usage`, one row per client/day in `client_ryka_usage_daily` (read-only, same-account RLS). The dashboard classifies with `src/lib/ryka/clinicUsage.ts`. Why: product names carry prefixes ("EC l …"), and usage history must come from Ryka, never be invented in ROY.
- People presentation uses `peopleVisibility.ts`: collection queries exclude technical account IDs before pagination/counts, and joined sector/agent lists use its identity predicate; current-user, auth, permission, billing and historical-author reads are not filtered. Why: technical sessions must remain functional without being presented as team members or changing business rules.
- The Clínica Ryka page scopes both Painel and Clientes by each client's contract situation: `pickClientContract` (src/lib/ryka/contractStatus.ts) picks one stored contract per client (in-force first, else most recent) and groups it through the contract catalog's `metric_bucket`; the export uses the same rows. Why: the ROY tab must match who is really active in Ryka without inventing a status or changing contracts.
- Practice-area rename, delete and stray-name moves go only through the RPCs `rename_practice_area`, `delete_practice_area` and `move_practice_area_label` (permission-checked, caller-account scoped, audited), which rewrite the name inside `clients`/`leads` `business_niche` in the same transaction; area names never contain commas and usage counts come from `practice_areas_usage`. Why: records store the area by name, so a catalog-only edit leaves them pointing at a name that no longer exists.
- Live mentoring has one record source, `ec_mentoring_attendance`: the Mentoria Ao Vivo page and the client's Agenda de Entregas (`ClientMentoringDeliveries`) read and write it, classify through `mentoringSessionStatus` (src/lib/mentoring/sessionStatus.ts) and invalidate each other's queries; no mirrored event or delivery rows; the client's default open mentoring row is display-only from `pendingMentoring` (active contract and no future date), never a stored row. Why: the team records a mentoring once and both screens must agree.
- Contract → product sync (`sync_contract_product`) only inserts a `client_products` link that does not exist yet, and `enforce_single_active_client_product` never deactivates the row of the same product. Why: BEFORE INSERT triggers run even when `ON CONFLICT DO NOTHING` discards the row, so every contract update used to push the client's active product to history.
